Multi-tenant security & isolation

71/100
verdict: accept-with-changes

Against the CONFIRMED v1 target (1-2 tenants, Workers Paid, Clerk, $400/mo configurable, scale-out deferred to Phase-N), the multi-tenant + intra-tenant isolation story is sound and no critical leak survives. All seven lens checks pass on both the read AND write sides. (1) §9.0.1/§7.2 membership resolution is tenant-bound: the lookup is WHERE user_id=? AND tenant_id=?, the active tenant is pinned per-surface and re-checked against memberships, and an unspecified tenant errors 401 (never a silent first-membership default) — a multi-tenant user is bound to exactly one tenant per request. (2) foldPartitionFilter collapses any number of granted scopes to a single {scope:{$in:[...]}} query, derived from the principal's own grant, and ScopedVectorize.query independently re-authorizes any explicit scope filter against allowedScopes, so no ungranted scope leaks; visibility is deliberately NOT pushed (correct — it would drop the principal's own private chunks). (3) The link-arm getLinks/expandFrontier are typed ScopedDB methods that apply nodeGate (scope AND visibility) to BOTH endpoints (nf/nt) with no raw-SQL escape hatch; the BFS, getLinks, and get_backlinks gate identically, and the seed is resolved through nodeVisible/resolveScopedNode before the walk. (4) trust_grade is genuinely absent from the entire vector path: the authoritative ChunkMeta upsert blob (§3.2/§4.9) enumerates exactly {documentId,teamId,scope,visibility,userId,embeddingModel,chunkIndex,path,tenant_id} with no trustGrade, it is not a metadata index, foldPartitionFilter folds only scope, and the trust boost runs post-hydration on the LEFT-JOINed sidecar. (5) Break-glass remains fail-closed (403 for non-admins, including a forged breakGlass:true), org-role-gated, writes a breakglass_read audit row in-batch, fires a high-severity alert every call, is intra-tenant only (never bypasses tenant_id), and is covered by canaries #14/#15. (6) Isolation is intact despite single-D1: ScopedDB injects tenant_id + scopePredicate + visibilityPredicate at one choke-point with an ESLint banned-import control, ScopedVectorize hard-wires namespace=tenantId with a D1 re-check as the correctness gate, and the §3.1.8 coverage matrix confirms chunks/facts/pages carry tenant_id+visibility+user_id+team_id (entities the {world,team} subset). Crucially the WRITE side backs the read predicates: §8.3 stamps the session's visibility/user_id/team_id onto transcript chunks (overriding the 'world' default that correctly applies only to org-knowledge ingested docs), chunks.visibility is NOT NULL DEFAULT 'world' CHECK-constrained, writeFact forces user_id=p.userId and constrains visibility by role, and §7.1 mint pins allowed_scopes=intersect(request, minter.allowedScopes) so a restricted member cannot one-step-escalate to tenant-wide. The only residue is non-load-bearing documentation debris: four Code-reference annotation lines still say 'trust_grade as metadata filter,' contradicting the (correct) authoritative body.
